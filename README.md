# LR

左右の Command キーの**単独押し**で、英数とかなを切り替える macOS メニューバーアプリ。

```
左 ⌘ を押して離す  →  ABC（英数）
右 ⌘ を押して離す  →  ひらがな
```

`⌘C` や `⌘⇧4` のときは切り替わらない。⌘ を押している間に他のキーやクリックが
挟まったら、その回は無かったことにする。

メニューバーには今のモードが `A` / `あ` で出る。Dock とアプリスイッチャには出ない。

もう1つ、[Rectangle](https://rectangleapp.com/) と同じキーで、手前のウィンドウを
半分・1/4・1/3 などに並べられる。ドラッグで画面の端へ寄せても並ぶ（下の「ウィンドウを並べる」）。

さらに、MacBook のノッチをクリックすると、カメラの映像が鏡として出てくる（下の「鏡」）。
元は [Kagami](https://github.com/finalize/kagami) という別のアプリだったものを取り込んだ。

初めて書いた Swift のコード。なので普段より注釈が多い。

## zip から入れる

Xcode が無くても、[Releases](https://github.com/finalize/lr/releases) にある `LR-<版>.zip` から入れられる。
macOS 14 以降。Apple シリコンでも Intel でも動く。

1. zip を開き、出てきた `LR.app` を **Finder で**「アプリケーション」フォルダへ移す
2. `LR.app` を開く。「“LR”は開いていません」と止められるので「完了」で閉じる
3. システム設定 > プライバシーとセキュリティ を開き、下の方にある
   「お使いのMacを保護するために“LR”がブロックされました。」の「このまま開く」を押す。
   パスワードを聞かれ、もう一度確かめられたら開く方を選ぶ
4. アクセシビリティの許可を求められるので与える（下の「アクセシビリティの許可」）
5. 初めて鏡を開いたときにカメラの許可を聞かれるので、許可する

2〜3 は、公証（Apple による事前の検査）を通していないために要る（下の「配る」）。
ターミナルを使うなら、2〜3 の代わりにこれでもよい:

```sh
xattr -dr com.apple.quarantine /Applications/LR.app
```

ダウンロードしたアプリを Finder で動かさずに開くと、macOS はそれを毎回違う場所に写してから
動かす（App Translocation）。許可を与える先を `/Applications/LR.app` に固定したいので、先に移す。

**新しい版を入れるとき**は、LR を終了してから `/Applications/LR.app` を置き換える。
2〜3 はもう一度要るが、アクセシビリティとカメラの許可はそのまま残る。どの版も同じ証明書で
署名しているから（下の「署名」「配る」）。

## 動かす

macOS 14 以降と Xcode が要る。

```sh
git clone https://github.com/finalize/lr.git
cd lr
./install.sh
```

Release ビルドを `/Applications/LR.app` に置いて起動する。初回はコード署名用の
自己署名証明書がこの端末に無いので、`install.sh` が `Cert/make-cert.sh` を呼んで
作ってからビルドする（login キーチェーンに入る。理由は下の「署名」）。

あとは**アクセシビリティの許可を与えれば使える。** 許可は端末ごと・OS ごとの
ものなので、別の端末では改めて与えることになる。

**Xcode の ⌘R ではなく `./install.sh` を使う。** Xcode が起動したアプリには
`get-task-allow`（デバッグ可の印）が付き、置き場所も DerivedData の中で変わりうるため、
許可を与える先が安定しない。コードを読む・直すのは Xcode で、試すのは `./install.sh` で。

`~/Applications` ではなく `/Applications` に置くのは、Finder 上の表示名が
どちらも「アプリケーション」で、許可を与えるときにどっちを見ているのか分からなくなるから。

## 中で何が起きているか見る

画面が無いアプリなので `print` は見えない。代わりに `Logger` に残してある。

```sh
log show --last 2m --predicate 'subsystem == "com.finalize.lr"' --style compact
log stream --predicate 'subsystem == "com.finalize.lr"'   # 流しながら見る
```

正常なら、起動時にこう出る:

```
起動した 英数=ABC かな=Hiragana
アクセシビリティ許可: あり
監視を開始した (登録できた=true)
```

打鍵ごとの細かいログは `debug` にしてあり、ディスクには残らない。追いたいときだけ
明示的に有効にする:

```sh
log stream --debug --predicate 'subsystem == "com.finalize.lr"'
```

⌘ を単独で押すと、こう流れる:

```
イベント 種別=12 flags=0x100108
イベント 種別=12 flags=0x100
単独押しが成立: 左
切り替え 英数 対象=com.apple.keylayout.ABC
```

**切り替わらないときはここを見る。**

| ログの出方 | 原因 |
| --- | --- |
| `アクセシビリティ許可: なし` のまま | 許可が与えられていない。システム設定 > プライバシーとセキュリティ > アクセシビリティ で LR をオンにする |
| `アクセシビリティ許可: なし` だがシステム設定のスイッチは ON | 記録が古い。上の「再ビルドすると許可が壊れる」へ |
| `監視を開始した` は出るが `イベント` が1行も出ない | 許可はあるがキーが届いていない。プライバシーとセキュリティ >「入力監視」にも LR を追加してみる。それでも駄目なら `NSEvent.addGlobalMonitorForEvents` を `CGEvent.tapCreate` に置き換える |
| `イベント` は出るが `単独押しが成立` が出ない | 単独押しの判定で落ちている。`flags` の値を見る。左 ⌘ で `0x8`、右 ⌘ で `0x10` のビットが立っているか |
| `切り替えに失敗` | `TISSelectInputSource` が拒否している。対象の入力ソースが無効になっていないか |

### 先に ⌘英かな を終了させる

`/Applications/⌘英かな.app` が動いていると、1回の ⌘ で両方が反応して競合する。
試すあいだは本家を終了しておく。

```sh
pkill -x '⌘英かな'    # メニューバーのアイコンから終了しても同じ
```

### アクセシビリティの許可

キー入力を覗くには許可が要る。許可が無いとき、`NSEvent.addGlobalMonitorForEvents`
は**エラーを返さずに黙って何も呼ばない**ので、「動かない理由が分からない」状態になる。
だからメニューに許可の有無を出してある。

許可が無いまま起動すると、アプリの方からダイアログを出す。これを出すと macOS が
**アクセシビリティの一覧に LR を自動で登録する**ので、あとはスイッチを入れるだけ。
`.app` を自分で探して「+」で追加する必要は無い。

1. 「システム設定を開く」を押す
2. 出てきた一覧の LR のスイッチをオンにする

ダイアログを閉じてしまったら、メニューバーの `A` をクリックして
「アクセシビリティ設定を開く…」で同じところに行ける。

ダイアログはアプリごとに一度しか出ない。一度断ったあとにもう一度出したいときは記録を消す:

```sh
tccutil reset Accessibility com.finalize.lr
```

許可が下りたかは1秒ごとに見に行っていて、下りたら監視が始まる。通常はアプリの再起動は
要らないが、切り替わらなければ一度終了して起動し直す。

### 署名 — 再ビルドで許可を壊さないために

自己署名の証明書で署名している。**これをやらないと、再ビルドのたびに許可が壊れる。**

```sh
./Cert/make-cert.sh    # 一度だけ。login キーチェーンに入る
```

ad-hoc 署名（`CODE_SIGN_IDENTITY = "-"`）には証明書チェーンが無いので、TCC は
許可の条件を**バイナリのハッシュ（cdhash）**で固定する。ビルドし直すとハッシュが
変わって一致しなくなるのに、**システム設定のスイッチは ON のまま残る**。
「許可済みに見えるのに一切動かない」という一番分かりにくい壊れ方をする。

証明書で署名すると、条件が証明書で書かれるようになる:

```sh
$ codesign -d -r- /Applications/LR.app
designated => identifier "com.finalize.lr" and certificate root = H"7146da…"
```

ハッシュを参照していない。実際、中身を変えて2回ビルドすると:

```
CDHash      9e242996… → a39fd3e9…   変わる
requirement 同一                     変わらない
```

Apple Developer への登録は要らない。信頼設定（GUI の認証が必要）も要らない。
`security find-identity` が `CSSMERR_TP_NOT_TRUSTED` と言っても、codesign は
信頼されていない自己署名の identity で問題なく署名できる。

別のマシンで `make-cert.sh` を走らせると別の証明書になるので、そのときは
許可を一度だけ与え直す。

#### それでも動かないとき

本当に効いているかは tccd のログで分かる:

```sh
log show --last 10m --predicate 'process == "tccd"' --style compact | grep -i "com.finalize.lr"
```

```
Failed to match existing code requirement for subject com.finalize.lr
and service kTCCServiceAccessibility     ← 記録が古い
```

```sh
tccutil reset Accessibility com.finalize.lr    # 消して与え直す
```

## ウィンドウを並べる

手前のアプリのウィンドウを、キー1つで決まった場所へ動かす。メニューの「ウィンドウ」からも選べる。
キーは Rectangle の既定と同じにしてある。

| キー | 操作 |
| --- | --- |
| `⌃⌥←` `⌃⌥→` `⌃⌥↑` `⌃⌥↓` | 左 / 右 / 上 / 下半分 |
| `⌃⌥U` `⌃⌥I` `⌃⌥J` `⌃⌥K` | 左上 / 右上 / 左下 / 右下 |
| `⌃⌥D` `⌃⌥F` `⌃⌥G` | 左 / 中央 / 右 1/3 |
| `⌃⌥E` `⌃⌥R` `⌃⌥T` | 左 / 中央 / 右 2/3 |
| `⌃⌥↩` | 最大化 |
| `⌃⌥⇧↑` | 高さだけ最大化 |
| `⌃⌥C` | 中央へ（大きさはそのまま） |
| `⌃⌥=` `⌃⌥-` | 大きく / 小さく |
| `⌃⌥⌫` | 元に戻す |
| `⌃⌥⌘←` `⌃⌥⌘→` | 前 / 次の画面へ |

縦長の画面では 1/3 と 2/3 が上下に分かれる（左 → 上、右 → 下）。

ウィンドウを動かすのにもアクセシビリティの許可が要るが、⌘ の単独押しのための許可で足りる。
ショートカットの登録そのものには許可は要らない。

### Rectangle と同時に動かさない

**同じキーを両方が登録する。** しかも登録はどちらも「成功」するので、LR の側からは
取り合いになっていることが分からない（Rectangle が動いている横で登録して確かめた）。

- LR で足りるなら、Rectangle を終了する
- Rectangle を使い続けるなら、LR のメニューの「ウィンドウ > ショートカットで動かす」を切る。
  メニューから選んで動かすのは、切っていても使える

Rectangle にあって LR に無いもの:

- 同じキーを続けて押したときの動き（1/3 → 中央 1/3 → 右 1/3 と送る、隣の画面へ送る、等）
- ショートカットの変更、ウィンドウ同士の隙間

### 決めたこと

- **1/3 を3つ並べても隙間も重なりも出ない。** 半分も 1/4 も 1/3 も「画面を等分した格子の
  何マス分か」で表し、境目の位置を1つの式（`始点 + round(長さ × k / n)`）で決めている。
  隣り合う領域は必ず同じ境目を共有する。Rectangle は操作ごとに端数の扱いが違い、
  1pt の隙間が出ることがある。
- **元に戻すと、LR が最初に動かす前の位置に戻る。** 左半分 → 右 1/3 → 最大化 と続けて
  動かしても、戻り先は左半分ではなく最初の位置（Rectangle と同じ）。ただし LR が置いた
  あとに手で動かしていたら、そこを新しい出発点として覚え直す。
- **次の画面へは、割合を保って移す。** 左半分にあったウィンドウは、大きさの違う画面へ
  移しても左半分に来る。大きさではなく四辺の位置を写すので、隣り合って並べていた2枚は
  移したあとも隣り合ったまま。Rectangle の既定は「大きさを保って真ん中に置く」なので、ここは違う。
  （元の画面の幅が奇数だと、端数のぶん 1pt ずれることはある。）
- **大きく・小さくでは、画面の端に付いた辺は動かさない。** 左半分のウィンドウを大きくすると
  右へだけ伸びる。高さがいっぱいのウィンドウは、小さくしても高さはいっぱいのまま
  （四辺とも端に付いている＝最大化しているときだけ、縦横とも縮む）。画面の 1/4 より小さくはしない。
  1回に 30pt。ここは Rectangle と同じ。
- **大きさを変えられないウィンドウ**（計算機など）は、大きさを保って行き先の真ん中に置く。
- **アプリの最小の大きさより小さく指示したとき**は、はみ出した分を画面の中へ押し戻す。
  元に戻すときだけは、元々はみ出して置かれていたかもしれないので押し戻さない。
- **フルスクリーンのウィンドウは動かさない。** 動かせないとき（ウィンドウが無い、画面が1枚しか
  無いのに次の画面へ、戻り先を覚えていない、これ以上小さくできない）はビープを鳴らす。
  ショートカットは画面に何も出さないので、黙っていると効かなかったのか分からない。
- **相手のアプリの返事は 0.5 秒までしか待たない。** AX の呼び出しは相手に問い合わせて待つので、
  相手が固まっていると LR のメインスレッドも止まる。⌘ の単独押しも同じスレッドで見ているので、
  待ち続けると英かなの切り替えまで効かなくなる。

### ドラッグで端へ寄せる（スナップ）

ウィンドウのタイトルバーを掴んで画面の端へ持っていくと、離したときにどこへ並ぶかが
半透明の枠で出る。そのまま離せば並ぶ。配置は、それまで Rectangle で使っていた設定を
そのまま移した（Rectangle の既定とは違う）。

```
┌─────────────┬──────────────────────┬─────────────┐
│ 左上の角     │ 上の辺                │ 右上の角     │
│ → 左半分     │ → 中央 1/3           │ → 右半分     │
├─────────────┘                      └─────────────┤
│ 左の辺                                  右の辺    │
│ → 左 1/3                               → 右 1/3  │
├─────────────┐                      ┌─────────────┤
│ 左下の角     │ 下の辺                │ 右下の角     │
│ → 左下       │ → 左・中央・右の 1/3  │ → 右下       │
└─────────────┴──────────────────────┴─────────────┘
```

- **辺は画面の端から 5pt、角は 25pt。** 角は、縦横どちらの端からも 25pt 以内。角を広く取らないと狙えない
- **下の辺はカーソルの位置で 1/3 が決まる。** 境目は 1/3 に並べたときの境目と同じ位置。左の 1/3 を出したまま
  下の辺に沿って中央へ滑らせると、左の 2/3 になる（右から滑らせれば右の 2/3）
- **Esc を押すと、そのドラッグではスナップしない。** 端で離しても並ばない
- **スナップしたウィンドウを引き剥がすと、元の大きさに戻る。** 掴んだ場所がウィンドウの外に出ないように、
  必要なら右へずらす。LR が置いたあとに手で大きさを変えていたら戻さない
- **元に戻す（⌃⌥⌫）は、ドラッグを始める前の位置へ。** 離した場所ではなく。スナップ済みのウィンドウを
  別の端へ運び直したときは、最初にスナップする前の位置のまま
- **大きさを変えるドラッグ（ウィンドウの端を掴む）ではスナップしない。** 大きさが変わらずに
  位置だけ変わったものを「動かしている」とみなす
- **縦長の画面ではスナップしない。** 縦長の画面の配置は決めていない。横長の配置を当てると
  1/3 が上下に分かれて「左の辺で上 1/3」のようなちぐはぐなことになる

**ホットコーナーを設定している角では、隅まで押し込むとホットコーナーも反応する。** 角の範囲は隅から
25pt あるので、隅の手前で離せばよい（Rectangle でも同じ）。試験で右下の隅（クイックメモ）まで
運んだときに、ここに気づいた。

メニューの「ウィンドウ > ドラッグで端に寄せて並べる」で切れる。macOS 15 以降は macOS 自身にも
端へ寄せて並べる機能があり（システム設定 > デスクトップと Dock > ウィンドウ）、両方が入っていると
1回のドラッグに両方が反応する。どちらか一方にする。

#### ドラッグの最中の位置は、アプリではなくウィンドウサーバーに尋ねる

最初は、動かしているかどうかを AX（アプリへの問い合わせ）で見ていて、まったくスナップしなかった。
ドラッグの最中にウィンドウを動かしているのはウィンドウサーバーで、アプリはあとからまとめて
知らされる。試験用のウィンドウで測ると、カーソルが 100pt 近く動いても AX の位置は動いておらず、
0.1 秒ごとにまとめて追いついていた。ウィンドウサーバーの位置はカーソルにぴったり付いてきた。

```
         ウィンドウサーバー   AX（アプリ）   カーソル
 264ms   288                 300           576
 353ms   216                 300           504
 385ms   180                 204           480
 485ms    96                 120           396
```

LR は「動かないままカーソルが 50pt 離れたら、文字の選択などウィンドウ以外のドラッグ」と見切っているので、
遅れた位置を見ていると、動き出したことに気づく前に見切ってしまう。いまは、マウスのイベントに入っている
ウィンドウの番号でウィンドウサーバーに位置を尋ねている（`DragSnapper.swift` の `WindowServer`）。
位置と大きさを読むだけなら画面収録の許可は要らない。

ウィンドウサーバーの位置も、**イベント1つ分は遅れる**（上の表でも、カーソルの 1 歩ぶん後ろを付いてくる）。
最初は1回の drag で 50pt を超えただけで見切っていたので、1歩目が大きい速いドラッグ（試験では 72pt）で
スナップも引き剥がしも起きなかった。いまは「**1つ前の** drag の時点で 50pt 離れていたのに、まだ動いて
いない」ときに見切る。

### 押しても動かないとき

押すたびの記録は `debug` なので、見るときだけ有効にする:

```sh
log stream --debug --predicate 'subsystem == "com.finalize.lr"'
```

正常なら、押すたびにこう出る:

```
ウィンドウ 左半分 アプリ=com.finalize.winprobe (300, 708, 600×432) → (0, 30, 1280×1345)
ウィンドウ 元に戻す をしない: 戻り先を覚えていない
```

座標は AX の向き（主画面の左上が原点、y は下向き）。上の例で高さが画面（1346）より 1 小さいのは、
アプリ側がそれ以上大きくならなかったため。

| ログの出方 | 原因 |
| --- | --- |
| 起動時に `ウィンドウのショートカットを登録した` が出ない | 「ウィンドウ > ショートカットで動かす」が切れている |
| 押しても `ウィンドウ …` が1行も出ない | キーが LR に届いていない。Rectangle など、同じキーを使うアプリが動いていないか |
| `ウィンドウ 左半分 をしない: …` | 理由がそのまま出る（ウィンドウが無い、フルスクリーン、等） |
| `ウィンドウに書き込めない … AXError=…` | そのアプリが位置や大きさの変更を断っている |
| `ウィンドウを動かせない: アクセシビリティの許可が無い` | 上の「アクセシビリティの許可」へ |
| ドラッグで端へ寄せても何も出ない | 起動時に `ドラッグでのスナップを始めた` が出ているか。許可が下りるまでは始めない |
| `掴んだウィンドウを見分けられないのでスナップしない` | AX で見つけたウィンドウと、ウィンドウサーバーのウィンドウの枠が食い違った。別のウィンドウを動かさないように、そのドラッグは見送っている |

スナップしたときは `ウィンドウ 左 1/3 …` が、引き剥がしたときは `スナップを外した …` が出る。

**ショートカットの試験は手で押すしかない。** `CGEvent` で ⌃⌥← を合成して送っても、
Carbon のショートカット（`RegisterEventHotKey`）は発火しなかった。LR の試験用に作った
受け手でも、Rectangle でも同じ（2026-09-23）。メニューから選ぶ道は、AX でメニューを
押して試せる（下の「確認できていること」）。

## 鏡

MacBook のノッチをクリックすると、カメラの映像が鏡として出てくる。ビデオ会議の前に顔や髪を
確かめるためのもの（[Hand Mirror](https://handmirror.app/) の自作版）。

```
        ┌──────┐  ← ノッチをクリック
 ───────┴──────┴──────────────
      ┌──────────────┐
      │              │   鏡像で映る
      │    (・_・)    │   端を掴んで好きな大きさに
      │              │   外をクリック / Esc / ⌘W で閉じる
      └──────────────┘
```

- **ノッチのクリックで開く。** メニューの「鏡を出す」でも開く（⌘ のアイコンの下に出る）。
  ノッチの無い Mac ではこちらを使う
- **大きさは自由。** 端を掴んで伸縮でき、次に開いたときもその大きさで出る
- **画質を選べる。** 自動 / 4K / 1080p / 720p / 540p / 480p。今のカメラで使えない段は灰色
- 閉じたらカメラを止める（緑のランプが消える）
- 開いても前面のアプリは変わらない（ビデオ会議のアプリからフォーカスを奪わない）

設定はメニューの「鏡」か、鏡の上で右クリック。**LR のメニューを開くと鏡は閉じる。**
メニューバーの ⌘ へのクリックも「外のクリック」として届くから（下の「決めたこと」）。
映りを見ながら画質などを変えるなら、鏡の上で右クリックする。
「外をクリックしても閉じない」を入れているときは閉じない。

初めて鏡を開いたときにカメラの許可を聞かれる（Mac ごとに一度）。

### Kagami から移るとき

Kagami は終了して消す（`/Applications/Kagami.app`）。両方が動いていると、ノッチの上に
透明な小窓が2枚重なる。

設定は引き継がない。アプリの ID が違い（`com.finalize.kagami` → `com.finalize.lr`）、
設定の置き場所も違うから。鏡の大きさ・カメラ・画質は選び直す。カメラの許可も LR に与え直す。

### ノッチの無い Mac で試す

開発機（Mac Studio + 外部ディスプレイ + USB カメラ）にはノッチが無い。ノッチのクリックは偽のノッチで試せる:

```sh
defaults write com.finalize.lr fakeNotch -bool true && pkill -x LR; sleep 1; open /Applications/LR.app
defaults delete com.finalize.lr fakeNotch && pkill -x LR; sleep 1; open /Applications/LR.app   # 戻す
```

メインの画面の上端中央（幅 200pt、メニューバーの高さ）に偽のノッチが置かれる。本物と同じく
透明で見えないので、メニューバーの真ん中あたりをクリックする。クリックが届いていれば
ログに `ノッチがクリックされた` と出る。

### 鏡を開いている間の ⌘

鏡の窓は、フォーカスを奪わずにキー（打鍵を受け取る窓）になる。Esc と ⌘W を受けるためだ。
すると開いている間の打鍵は、他のアプリではなく LR に届く。⌘ の単独押しを見ている
グローバルモニタは**他のアプリ宛て**のイベントしか見ないので、そのままでは切り替わらなくなる。

Kagami が別のアプリだったころは起きなかった（Kagami 宛ては LR から見て「他のアプリ宛て」）。
取り込んで初めて出るので、LR 宛てを見るローカルモニタも置き、同じ判定に流している
（`CommandKeyWatcher.start`）。1つのイベントはどちらか片方にしか来ないので、二重には数えない。
ローカルモニタを外すと、鏡を開いている間は右 ⌘ を押してもかなに切り替わらないことを確かめた。

### 中で何が起きているか見る

ログは LR と同じ `com.finalize.lr` に出る。MacBook で正常なら、起動時と鏡を開いたときに
こういう形で出る（名前と数字は機種による）:

```
ノッチを見つけた: <内蔵ディスプレイの名前> {{x, y}, {幅, 高さ}}
映している: <カメラの名前> 画質=auto 実際=<幅>×<高さ>
カメラを止めた
```

| ログの出方 | 見るところ |
| --- | --- |
| `ノッチのある画面が無い` | 蓋を閉じて外部ディスプレイだけで使っている、またはノッチの無い Mac |
| `ノッチを見つけた` の矩形が実際のノッチとずれている | `NotchGeometry.notchRect`。`auxiliaryTopLeftArea` / `TopRightArea` の幅から出している |
| ノッチを見つけたのに、クリックしても何も出ない | `NotchTrigger` の小窓にクリックが届いていない |
| `実際=` が選んだ画質と違う | プリセットは「その程度」を頼むだけで、何が出るかはカメラ次第。手元の USB カメラは 720p を選んでも 1920×1080 のままだった |

### 決めたこと

- **メニューバーのアイコンは LR の ⌘ だけ。** Kagami のアイコン（左クリックで鏡、右クリックで設定、
  見た目を6種から選べた）は持ってこなかった。LR のメニューは SwiftUI の `MenuBarExtra` で、
  左クリックに別の動きを割り当てられない。アイコンを2つ並べるより、メニューに「鏡を出す」を置いた。
  アイコンの位置は `MenuBarExtra` が教えてくれないので、鏡はクリックしたときのマウスの真下に出す。
- **ポップオーバーではなくパネル。** `NSPopover` はユーザーが端を掴んでリサイズできない。
  `.nonactivatingPanel` にしてあるので、開いても前面のアプリが変わらない。
- **映像は切り抜いて敷く（`.resizeAspectFill`）。** 窓の縦横比を自由に変えられるので、
  黒帯を出すより鏡らしい。
- **画質はプリセットで選ぶ。** iOS のように形式を直接選んでセッションを「入力優先」にする
  `AVCaptureSessionPresetInputPriority` は macOS では使えない。
- **外をクリックしたら閉じる、の判定はグローバルモニタ。** 窓がキーでなくなったこと
  （resignKey）で判定すると、ノッチをクリックしたときに「閉じた直後にまた開く」が起きやすい。
  ノッチの小窓は LR の窓なので、そこへのクリックはグローバルモニタに来ない。
  ただし**メニューバーの LR のアイコンへのクリックは来る**（macOS 27 で確かめた。Kagami の
  注釈は来ないと書いていたが、違った）。LR のメニューを開くと鏡が閉じるのはこのため。
  ほかの外のクリックと同じ扱いで困らないので、避けていない。
- **メニューは SwiftUI と AppKit で2回書いてある。** LR のメニューの「鏡」は SwiftUI、
  鏡の上の右クリックは `NSMenu`（`MirrorModel.makeMenu`）。SwiftUI で書いたメニューを
  NSView の右クリックに渡す `NSHostingMenu` は macOS 15 からで、LR は 14 でも動かしたい。
- **鏡の設定の値は、本当の持ち主に置いたまま。** 鏡像か・閉じないか・カメラ・画質は UserDefaults、
  開いているかは窓、カメラの一覧はカメラ自身が持つ。`MirrorModel` は読まれるたびにそこへ聞く。
  メニューに変化を伝えるやり方は下の「Swift で戸惑ったところ」。

## アイコン

```sh
./Icon/build-icon.sh            # 白い ⌘（既定）
./Icon/build-icon.sh dark bold  # 濃い ⌘
```

1024 の PNG を1枚描いて、あとは `sips` で縮小するだけ。デザインツールは使わない。
`Icon/make-icon.swift` が全部やっている。

決めたこと:

- **グラデーションは色を採って引き直した。** 元にした画像は他所のブランドの素材なので、
  ビットマップをそのまま持ってこない。9×9 で色を採ったところ、右上と左下がほぼ同色
  （`#FB8967` と `#FF9D62`）だった。つまり等色の帯が対角に垂直に走っている＝
  左上→右下の単純な線形グラデーションで再現できる。対角線上の9点を stop にしてある。
- **角は円弧ではなく superellipse。** Apple のアイコンの角丸は `|x/a|^n + |y/b|^n = 1` を
  n=5 で描いた形に近い。`CGPath(roundedRect:)` の円弧だと微妙に違う。
- **中央寄せはフォントのメトリクスを使わない。** ascender / descender で中央を出すと
  上にずれる。字形の周りの余白はフォントの都合で決まっていて、見た目の重心とは
  関係がないからだ。一度別のレイヤーに描いて、アルファが立っている範囲を走査して
  実際の輪郭を求め、その中心を合わせている。
- **影は焼き込まない。** macOS 26 が自前で付ける。
- 白い ⌘ は中央付近の背景（`#FFA05C`）に対してコントラスト比 **2.0:1**、濃色版は
  **8.2:1**。アイコンに WCAG は適用されないが、線を太く（bold）したのはこのため。

## メニューバーのアイコン

SF Symbols の `command` を使っている。**アプリのアイコンのグラデーションはここには
使えない。** メニューバーは単色（テンプレート画像）しか受け付けず、色を付けても
明暗に合わせて全部塗り潰される。

既定ではアイコンだけを出し、モード（A / あ）は出さない。macOS 自身の入力メニューが
既に同じものをメニューバーに出していることが多く、隣に並べても二重になるだけだから。

```sh
defaults read com.apple.TextInputMenu visible   # 1 なら system 側が出ている
```

システムの入力メニューを消しているなら、メニューから「メニューバーに A / あ も出す」を
オンにすると状態が見えるようになる。

| `LR/MenuContent.swift` | クリックで開くメニューの中身 |
| `LR/AppModel.swift` | 状態と、状態を変える手続き。許可の監視もここ |

| `LR/WindowArranger.swift` | ウィンドウを動かす手順。下の3つをつなぐだけ |

| `LR/WindowHistory.swift` | 元に戻す先の記録 |

| `LR/DragSnapper.swift` | ドラッグでのスナップ。マウスを覗き、`SnapTracker` の言うとおりに動かす |
| `LR/SnapLayout.swift` | 端の判定と配置、1回のドラッグの解釈（`SnapTracker`）。画面にもウィンドウにも触らない |
| `LR/SnapPreview.swift` | ドラッグ中に行き先を見せる半透明の枠 |
| `LR/MirrorModel.swift` | 鏡の部品をつなぎ、メニューに状態を見せる。鏡の上の右クリックのメニューもここ |
| `LR/NotchTrigger.swift` | ノッチの上に透明な小窓を置いてクリックを拾う |
| `LR/NotchGeometry.swift` | ノッチの矩形の計算。画面には触らない |
| `LR/MirrorPanel.swift` | 鏡の窓。フォーカスを奪わないリサイズ可能なパネル、鏡像、外クリックで閉じる |
| `LR/PanelPlacement.swift` | 鏡の窓をどこに出すかの計算 |
| `LR/Camera.swift` | カメラのセッションの開始・停止、カメラと画質の切り替え |
| `LR/Quality.swift` | 画質の選択肢 |

`LRApp` → `CommandKeyWatcher` → `InputSource` の順に読むと、
「メニューバーに出す」「⌘ を見張る」「切り替える」の3つに分かれているのが見える。

ウィンドウのほうは `HotKeys` → `WindowArranger` → `WindowLayout` → `AXWindow` の順。
「キーを受け取る」「行き先を決める」「動かす」に分かれていて、真ん中の計算だけが
画面もウィンドウも使わずに試せる。

スナップは `DragSnapper` → `SnapLayout`（の `SnapTracker`）→ `WindowArranger`。
`SnapTracker` は `CommandKeyWatcher` と同じ形で、押す・動かす・離すを受け取って
「何をすべきか」を返すだけなので、マウス無しで試せる。

鏡は `NotchTrigger` → `MirrorModel` → `MirrorPanel`（の `MirrorController`）→ `Camera`。
「クリックを拾う」「つなぐ」「窓を出す」「映す」に分かれていて、ノッチの位置と窓の置き場所の
計算（`NotchGeometry` / `PanelPlacement`）だけが、画面もカメラも使わずに試せる。

## テスト

```sh
./run-tests.sh
```

画面もキーボードも使わずに確かめられる4つを試す。

**単独押しの判定**（`Tests/WatcherTests.swift`）。合成した `NSEvent` を流し込んで確かめる。
実際のキーボードを叩くテストは書けない（許可が要る、機械にやらせにくい）ので、判定を
`CommandKeyWatcher.process(_:)` に切り出して、そこだけ単体で呼べるようにした。

`⌘C`、`⌘⇧4`、⇧ を先に押した場合、左右同時押し、`⌘` + クリック、Caps Lock 入り、
連続での単独押し ── 全部ここで押さえている。

**ウィンドウの行き先の計算**（`Tests/WindowLayoutTests.swift`）。`WindowAction.target` は
画面の並びとウィンドウの枠を引数で受け取るだけなので、画面を自分で組み立てて渡せば、
手元の画面が1枚でも、縦長の画面や2段に並べた画面を試せる。

- 値で固定したもの: 各操作の例、端数の丸め、縦長・正方形の画面での 1/3、大きく・小さくの
  端の扱いと下限、画面の並び、元に戻す先の引き継ぎと覚え直し
- 性質で見たもの: 3つの 1/3・左右の半分・4つの 1/4 が隙間も重なりもなく画面を埋める、
  隣り合う2枚は別の画面へ移しても隣り合ったまま、次の画面 → 前の画面で元に戻る、など。
  画面の大きさは奇数の幅や 3 で割り切れない幅も混ぜて 70 通り

このテストは、実装を見ていない別のエージェントに**決めごとだけ**を渡して書かせた。
実装を読んで書くと、今の実装の写しになって間違いも一緒に通してしまうから。通ったあとに
実装のほうを1か所ずつ壊して、落ちることを確かめてある（演算子の入れ替え 236 通りのうち
225 通りで落ち、残りは出力が変わらないものだった。「辺ではなく大きさを写す」
「元に戻す先を毎回覚え直す」のように決めごとそのものを崩しても落ちる）。

**ドラッグでのスナップ**（`Tests/SnapLayoutTests.swift`）。端の判定（5pt と 25pt の境目、角と辺の
優先）、端ごとの配置の表、下の辺の3分割と 2/3 への広がり、スナップを外すときの大きさとずらし方、
1回のドラッグの解釈（`SnapTracker`）。`SnapTracker` には、押す・動かす・離す・Esc を並べて渡し、
返ってきた「すべきこと」の列を見る。大きさを変えるドラッグ、動かないまま 50pt 離れたドラッグ、
Esc のあとで離したドラッグでは置かないこと、ウィンドウの枠を読む（相手に問い合わせる）のは
動き出す前だけなことも、ここで押さえている。これも決めごとだけを渡して別のエージェントに書かせ、
実装を壊して落ちることを確かめた（99 通りのうち 96 通りで落ち、残りは外から区別できないもの）。

別のエージェントが挙げた曖昧な点から、決めごとを1つ改めた。スナップするかどうか（横長か）と、
下の辺の3分割の境目を、画面全体（frame）ではなく visible で決める。1/3 の向きと境目を決めているのが
visible なので、frame で決めると Dock を横に置いた画面で「カーソルのある区画」と「出てくる枠」が
ずれる。改める前の版に戻すと落ちるテストを3件入れてある。

**鏡のノッチの位置・窓の置き場所・画質**（`Tests/MirrorTests.swift`）。Kagami から持ってきたもの。
ノッチの矩形（原点がずれた画面を含む）、偽のノッチ、窓を画面からはみ出さないように置くこと、
画質の読み戻しと、使えない段を自動に落とすこと。Kagami にあったメニューバーのアイコンのテストは、
アイコンを持ってこなかったので外した。

AX でウィンドウを読み書きする部分（`AXWindow`）と、ショートカットの受け取り
（`HotKeys`）、マウスの見張り（`DragSnapper`）はここでは試せない。前者は試験用のウィンドウを出して手で確かめた
（下の「確認できていること」）。

## 配る

```sh
./release.sh    # dist/LR-<版>.zip ができる
```

版は Xcode のターゲットの General > Version（`MARKETING_VERSION`）で上げてから作る。
できた zip を GitHub の Releases に添付する。受け取った人の手順は上の「zip から入れる」。

決めたこと:

- **公証（notarization）はしない。** 公証には Developer ID の証明書が要り、それには有料の
  Apple Developer Program が要る。この端末にある「Apple Development」の証明書では公証できない。
  代わりに、受け取った人に「このまま開く」を1回押してもらう。
- **配る版はいつも同じ証明書で署名する。** 受け取った人の許可は証明書に結び付いている
  （上の「署名」）ので、証明書が同じなら版を上げても許可が残る。別の証明書にすると、
  受け取った人全員の手元で「スイッチは ON なのに一切動かない」が起きる。自分の端末なら
  `install.sh` が記録を消して直すが、人の端末には手が届かない。だから `release.sh` は、
  署名の条件が今までと違えば zip を作らずに止まる（期待する値は `release.sh` の `CERT_ROOT`）。
  `install.sh` と違って、証明書が無くても作らない。
- **証明書はこの端末の login キーチェーンにしか無い。** 失くすと上と同じことが起きる。
  キーチェーンアクセスで「LR Code Signing」を `.p12` に書き出して、別に取っておく。
  別の端末で配布物を作るときも、`make-cert.sh` で作らずにこれを取り込む。
- **zip に拡張属性を入れない。** ビルドした `.app` のファイルには `com.apple.provenance` が付いていて、
  `ditto` は既定でこれを `._LR` のようなファイルにして zip に入れる。Finder で解けば属性に戻るが、
  `unzip` で解くと `.app` の中にファイルが増えて、署名が `a sealed resource is missing or invalid`
  で壊れる（確かめた）。`release.sh` は作った zip を `ditto` と `unzip` の両方で解き、署名が
  通ることを確かめてから終わる。通らなければ zip を消して止まる。

## Swift で戸惑ったところ

TypeScript / Go からの対応:

| Swift | 近いもの |
| --- | --- |
| `struct` | Go の構造体。代入でコピーされる値型 |
| `class` | 参照型。1つの実体を共有したいとき（`AppModel` がこれ） |
| `T?`（Optional） | `T \| undefined`。ただし中身を使うには毎回開ける必要がある |
| `guard let x = y else { return }` | 早期 return 付きの分割代入 |
| `init?` | 失敗を例外ではなく `nil` で返す初期化 |
| `protocol` | interface |
| `enum` | 取りうる値が型で閉じる。switch の漏れをコンパイラが指摘する |
| `some View` | 「View を満たす何らかの型」。具体名を書かなくていい |
| `@State` | `useState`。持ち主とライフタイムを View に揃える |
| `@Observable` | 読まれたプロパティを自動で追跡する。依存配列は要らない |
| `[weak self]` | 循環参照を切る。self がクロージャを持つときは基本これ |
| `Unmanaged` | C の API が返す生ポインタの所有権を、自分で宣言して受け取る |

`Unmanaged` の `takeUnretainedValue()` と `takeRetainedValue()` の選択だけは
間違えるとクラッシュするか漏れるので、`InputSource.swift` の注釈に理由を書いてある。

ほかに、ウィンドウの機能を足したときに引っかかったこと:

- **`@Observable` のクラスでは、init の中の代入でも `didSet` が走る。** ふつうのクラスでは
  走らない。副作用（ショートカットの登録）を `didSet` に置くなら、値が変わったときだけに絞る。
- **Carbon と SwiftUI に同じ名前の型 `EventModifiers` がある。** 両方を import すると
  「曖昧」と言われるので `SwiftUI.EventModifiers` と書く。
- **`CGWindowListCreateDescriptionFromArray` に渡す配列の中身は、数ではなくポインタ。**
  ウィンドウの番号をそのままポインタの値として詰める。Swift の配列を `as CFArray` で
  渡すと中身が CFNumber になり、エラーも出ずに空の結果が返ってくる。
- **C の関数ポインタには、周りの変数を掴んだクロージャを渡せない。** Carbon のイベントの
  受け口には self を `Unmanaged.passUnretained(self).toOpaque()` で `void *` にして別に渡し、
  呼ばれた側で取り出す（`HotKeys.swift`）。

鏡を取り込んだときに引っかかったこと:

- **`@Observable` は、自分で持っていない値の変化に気づけない。** UserDefaults や `SMAppService` に
  置いた値を計算プロパティで見せても、メニューは古いまま残る。値が1つなら、`@Observable` が
  class に足している `access(keyPath:)` / `withMutation(keyPath:)` で「読んだ」「変えた」を手で伝える
  （`AppModel.launchesAtLogin`）。たくさんあるなら、変わったら進める数を1つ持ち、どの値も読む前に
  それを読む（`MirrorModel.revision`）。
- **メニューの中の Picker の項目には `.disabled` が効かない。** 使えない画質が灰色にならなかった。
  前後に区切り線も勝手に入る。印の付く Toggle を並べて代えた（`MenuContent.choice`）。
- **`[weak self]` は外側のクロージャに付ける。** 内側にだけ付けると、内側に渡すために外側が
  self を強く掴む。Xcode 27 はこれを警告する（Kagami から持ってきた `Camera.start` で出た）。
- **`@MainActor` の印が付いた型は、印の無い型の init からは作れない。** 鏡の部品は `@MainActor` で
  書かれていたので、印の無い `AppModel` に混ぜず、`MirrorModel` を別に作って `LRApp` に持たせた。

## 作りとして決めたこと

- **入力ソースの ID を決め打ちしない。** US 配列なら `com.apple.keylayout.US` だし、
  ABC を無効にしている人もいる。「有効なキーボードレイアウトのうち好みの順で最初の1つ」
  「日本語を扱う入力モードのうち最初の1つ」という探し方にした。ことえりでも
  Google 日本語入力でも同じコードで通る。
- **`CGEvent` でキーコードを投げる回避策は使わない。** `TISSelectInputSource` が
  バックグラウンドプロセスからでもことえりのひらがなモードに効くことを先に確かめた。
- **イベントは覗くだけで消さない。** `⌘` の単独押しはほとんどのアプリで何もしないので、
  横取りして消す必要が無い。消す必要が出たら `CGEvent.tapCreate` に移る。

分かっている取りこぼし: **⌘ を押しながらドラッグすると、離したときに切り替わる。**
監視しているのは `mouseDown` だけで `mouseDragged` を見ていないため。下の
「長押しでは切り替えない閾値」を入れると大体消える。

## 次にやると面白いこと

- `.menuBarExtraStyle(.window)` にすると、メニューの代わりにふつうの SwiftUI が置ける。
  `Text` と `Button` しか使えない制約が外れる。
- メニューバーの `A` / `あ` を SF Symbols のアイコンにする。
- 長押しでは切り替えない閾値（`⌘` を 0.3 秒以上押していたら無視）。
- `run-tests.sh` を Xcode のテストターゲットに移す。`swift-testing` の `#expect` が使える。
- 縦長の画面でのスナップの配置を決める。
- 同じキーを続けて押したときに、1/2 → 2/3 → 1/3 と大きさを送る。
- ショートカットを変えられるようにする。
